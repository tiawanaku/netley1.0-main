Recomendación técnica para el desarrollador

Para evitar mantener tres módulos separados (Citas, Llamadas y Reuniones), implementen un único modelo Agenda con un campo tipo (cita, llamada, reunion) y relaciones opcionales (caso_id, consulta_id, cliente_id). Los comportamientos específicos pueden resolverse mediante formularios dinámicos y políticas de validación. Esto simplifica el mantenimiento, facilita la integración con Filament FullCalendar y hace más sencillo aplicar permisos posteriormente con Filament Shield.

Nota técnica para el desarrollador

El Portal del Cliente Ejecutivo no debe tener lógica de negocio propia para crear procesos, finanzas o agendas. Debe actuar como una capa de presentación que consulta los dominios del Backoffice y restringe el acceso únicamente a la información del cliente autenticado. Recomendación técnica

Cuando más adelante el dominio Persona sea compartido por Personal, Cliente Ejecutivo y otros tipos de usuarios, conviene que el sistema de autenticación sea independiente de la entidad Persona. Una buena práctica es mantener una tabla users donde el usuario sea el número de teléfono (único), y relacionarla con la persona correspondiente. De esta forma, si en el futuro incorporas autenticación por correo electrónico, autenticación multifactor o inicio de sesión con otros identificadores, no tendrás que modificar el modelo de negocio, sino únicamente la lógica de autenticación. Esta arquitectura también facilitará la integración con Filament Shield para la gestión de roles y permisos.

Estos cambios corresponden al dominio Agenda y pueden incorporarse como una mejora del módulo sin crear un nuevo sprint.

Recomendación técnica

Como el proyecto utilizará Filament FullCalendar, es recomendable implementar un único proveedor de eventos y adaptar el contenido mostrado según el rol del usuario autenticado. De esta manera:

Este enfoque evita duplicar la lógica del calendario y simplifica el mantenimiento cuando se integren los permisos mediante Filament Shield.
